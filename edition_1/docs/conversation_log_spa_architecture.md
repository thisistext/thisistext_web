# SPA 전환 검토 대화 기록

> **날짜**: 2025-12-15  
> **주제**: this is text 사이트의 SPA 전환 검토 및 아키텍처 결정

---

## 📋 논의 배경

사용자가 현재 MPA(Multi-Page Application) 방식으로 구성된 `thisistext_web` 사이트를 SPA로 전환하는 것에 대해 문의함.

### 현재 사이트 구조
- 5개의 독립 HTML 파일: `index.html`, `publishers.html`, `programs.html`, `sponsors.html`, `info.html`
- 공통 CSS: `style.css`
- GitHub Pages로 정적 호스팅

---

## 🔍 MPA vs SPA 비교 분석

### 현재 방식 (MPA) 장점
| 장점 | 설명 |
|------|------|
| 단순함 | 빌드 도구 없이 HTML/CSS만으로 동작 |
| SEO 친화적 | 각 페이지가 고유 HTML → 검색엔진 인덱싱 용이 |
| 빠른 초기 로딩 | JavaScript 번들 없이 바로 렌더링 |
| 유지보수 용이 | 각 페이지가 독립적 |
| 호스팅 비용 | GitHub Pages로 무료 |

### 현재 방식 (MPA) 단점
| 단점 | 설명 |
|------|------|
| 페이지 전환 깜빡임 | 매번 전체 페이지 리로드 |
| 중복 코드 | 헤더, 푸터, 사이드바 코드가 모든 HTML에 중복 |
| 상태 유지 어려움 | 페이지 간 상태 공유 불가 |

### SPA 장점
| 장점 | 설명 |
|------|------|
| 부드러운 전환 | 페이지 이동 시 화면 깜빡임 없음 |
| 컴포넌트 재사용 | 헤더, 푸터, 메뉴 등을 한 번만 정의 |
| 상태 관리 | 전역 상태로 페이지 간 데이터 공유 가능 |
| 풍부한 인터랙션 | 애니메이션, 실시간 업데이트 용이 |

### SPA 단점
| 단점 | 설명 |
|------|------|
| 초기 로딩 지연 | JavaScript 번들 다운로드 필요 |
| SEO 복잡성 | SSR/Prerendering 없이 인덱싱 어려움 |
| 빌드 환경 필요 | Node.js, npm, 빌드 도구 설정 필요 |
| GitHub Pages 제약 | 클라이언트 라우팅 추가 설정 필요 |

## 🎯 추가 요구사항 (사용자 입력)

1. **연간 반복 행사** - 매년 같은 행사를 개최할 예정
2. **매년 다른 디자인** - 연도별로 완전히 다른 디자인 적용 희망
3. **아카이빙** - 이전 연도 콘텐츠를 확인할 수 있는 아카이브 페이지 필요

## 🏗️ 제안된 아키텍처 옵션

### 옵션 1: MPA + 연도별 폴더 구조
```
thisistext_web/
├── index.html          ← 연도 선택 페이지
├── 2026/
│   ├── index.html
│   ├── style.css       ← 2026년 고유 디자인
│   └── ...
├── 2027/
│   ├── style.css       ← 2027년 새 디자인
│   └── ...
```
- ✅ 연도별 100% 다른 디자인 가능
- ❌ 공통 요소 수정 시 모든 연도 파일 수정 필요

### 옵션 2: SPA + 연도별 테마
```
thisistext_web/
├── src/
│   ├── themes/2026/, themes/2027/
│   ├── data/2026.json, 2027.json
│   └── components/     ← 공통 컴포넌트
```
- ✅ 공통 컴포넌트 재사용
- ❌ 빌드 환경 필요, 디자인 자유도 제한

### 옵션 3: 하이브리드 (추천 🌟)
```
thisistext_web/
├── index.html          ← 아카이브 허브 페이지
├── 2026/               ← 2026년 독립 사이트
├── 2027/               ← 2027년 완전히 새로운 디자인
```
- ✅ **매년 100% 자유로운 디자인**
- ✅ 각 연도가 타임캡슐처럼 보존
- ✅ 빌드 도구 불필요
- ✅ 현재 작업물 그대로 활용 가능

---

## ✅ 최종 추천

**하이브리드 방식 (옵션 3)**을 추천

### 이유
1. **디자인 자유도 100%** - 매년 완전히 새로운 느낌 가능
2. **과거 보존** - 이전 연도 사이트가 그대로 유지됨 (타임캡슐 효과)
3. **복잡도 낮음** - HTML/CSS만으로 작업 가능
4. **아카이브 효과** - `/2026`, `/2027`로 바로 접근 가능
